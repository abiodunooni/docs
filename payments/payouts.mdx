Payments collects money. Sending it out is a separate job, and there are two ways to do it:

| | Dashboard | Wallets API |
| --- | --- | --- |
| Effort | None | An integration |
| Bulk | CSV upload | Loop over recipients |
| Scheduling | Manual | Whatever you build |
| Best for | Occasional or ad-hoc payouts | Automated, recurring or high-volume |

<Note>
  Payments has no payouts API of its own. Programmatic payouts run on the [Wallets API](/wallets), which uses the same Quidax account and one secret key.
</Note>

## The payout wallet

Your payout wallet is separate from your collection wallet, so money coming in and money going out stay apart.

Fund it by settling collections into it, or receive into it directly: **Payout → Receive**, pick a currency, and share the generated address.

## Paying out from the dashboard

### One recipient

<Steps>
  <Step title="Open Payout → Send → Single Transfer">
    Choose the currency, pick a saved beneficiary or enter new details, and enter the amount.
  </Step>

  <Step title="Review and confirm">
    Check the details, tick the confirmation box, confirm.
  </Step>
</Steps>

### Many recipients, with a CSV

<Steps>
  <Step title="Prepare your beneficiaries">
    **Settings → Beneficiary settings → Add bulk beneficiaries.** Click **Download template** first — the columns must match it exactly.

    | Column | Contents |
    | --- | --- |
    | Alias | A name to identify the recipient |
    | Wallet address | Where funds go |
    | Currency | The currency that address is for |

    Upload the file. Every valid row is added; invalid rows are skipped, so check the count afterwards.
  </Step>

  <Step title="Open Payout → Send → Bulk Transfer">
    Either select recipients from a list you already uploaded, or upload a new CSV containing recipients **and amounts**.
  </Step>

  <Step title="Review the confirmation page">
    Every recipient and amount is listed. This is your last chance to catch a bad row — crypto payouts cannot be reversed.
  </Step>

  <Step title="Confirm">
    The batch is submitted.
  </Step>
</Steps>

<Warning>
  Check the recipient count and total on the confirmation page against your source file. A CSV with a shifted column or a stray row will pay the wrong people the wrong amounts, and there is no recall.
</Warning>

<Tip>
  Run a first batch with two recipients and trivial amounts before running one with two hundred. It costs almost nothing and proves your file format end to end.
</Tip>

## Paying out through the Wallets API

Same account, same key, one endpoint. What you put in `fund_uid` decides the rail.

| `fund_uid` contains | Result |
| --- | --- |
| A blockchain address | On-chain payout |
| A Quidax account ID | Internal transfer — instant and free |
| A bank account number | Fiat payout, with `fund_uid2` as the bank code |

### A single payout

<Steps>
  <Step title="Check the balance and the network">
    ```bash
    curl 'https://openapi.quidax.io/exchange-open-api/api/v1/users/me/wallets/usdt' \
      -H "Authorization: Bearer $QUIDAX_SECRET_KEY"
    ```

    **Spendable balance is `balance` alone** — `locked` and `staked` are committed. In the `networks` array, confirm your network has `withdraws_enabled: true`.
  </Step>

  <Step title="Generate and store a reference">
    Before you call. If the request times out, this is the only way to find out what happened.
  </Step>

  <Step title="Submit">
    ```bash
    curl -X POST 'https://openapi.quidax.io/exchange-open-api/api/v1/users/me/withdraws' \
      -H 'accept: application/json' \
      -H 'content-type: application/json' \
      -H "Authorization: Bearer $QUIDAX_SECRET_KEY" \
      -d '{
        "currency": "usdt",
        "amount": "250",
        "fund_uid": "<wallet_address>",
        "network": "trc20",
        "reference": "payout-1024",
        "narration": "October payout"
      }'
    ```

    **You get back** a withdrawal with `status: processing`.

    **Always send `network`.** Omitting it uses the currency default, and a mismatch loses the funds.
  </Step>

  <Step title="Wait for the outcome">
    **Expect** `withdraw.successful` or `withdraw.rejected`. A rejection carries a `reason` — read it before retrying, because most rejections repeat.
  </Step>

  <Step title="Reconcile">
    ```bash
    curl 'https://openapi.quidax.io/exchange-open-api/api/v1/users/me/withdraws/reference/payout-1024' \
      -H "Authorization: Bearer $QUIDAX_SECRET_KEY"
    ```

    `total` is what actually left the wallet, after `fee`.
  </Step>
</Steps>

### A batch, without a CSV

There is no bulk endpoint. A batch is a loop, and the loop needs to be resumable.

<Steps>
  <Step title="Build the batch in your own store">
    One row per recipient, each with a **pre-generated unique reference** and a state of `pending`. Persist this before you call anything.

    A good reference encodes the batch: `payout-2026-04-batch7-0042`.
  </Step>

  <Step title="Check the total against your balance">
    Sum the batch and compare against `balance` plus expected fees. Running dry halfway through leaves you reconciling a partial batch.
  </Step>

  <Step title="Submit one at a time, inside the rate limit">
    300 requests per minute. Roughly one every 250ms leaves headroom for retries.

    Mark each row `submitted` **before** the call and record the response after it. A row you submitted but have no response for is the dangerous case, and the next step handles it.
  </Step>

  <Step title="Resolve anything uncertain by reference">
    For every row still `submitted` with no confirmed outcome:

    ```bash
    curl 'https://openapi.quidax.io/exchange-open-api/api/v1/users/me/withdraws/reference/<reference>' \
      -H "Authorization: Bearer $QUIDAX_SECRET_KEY"
    ```

    | Response | Meaning | Action |
    | --- | --- | --- |
    | A withdrawal | It landed | Record it. **Do not resubmit.** |
    | `110112` | It never landed | Safe to resubmit with the same reference. |
  </Step>

  <Step title="Reconcile on the webhooks">
    Mark rows complete on `withdraw.successful`, failed on `withdraw.rejected`. Process idempotently — the same event can arrive twice.
  </Step>
</Steps>

<Warning>
  Never retry a payout with a **new** reference. If the original landed, you have paid twice, and an on-chain payout cannot be recalled. The reference is what makes a retry safe.
</Warning>

<Tip>
  Route internal recipients — anyone who also holds an account with you — by account ID rather than address. Instant, free, and no possibility of a wrong-network loss.
</Tip>

### Ingesting a CSV yourself

If your finance team works in spreadsheets but you want the API to run the batch:

<Steps>
  <Step title="Parse and validate before submitting anything">
    Reject the whole file if any row fails. Half a payroll run is worse than none.

    | Check | Why |
    | --- | --- |
    | Address is present and well-formed for the network | Wrong addresses are unrecoverable |
    | Currency is supported and `withdraws_enabled` on that network | Otherwise every row fails |
    | Amount is a positive number within sane bounds | Catches a shifted column |
    | No duplicate recipient rows | Catches a copy-paste error |
    | Total is within your balance | Catches running dry mid-batch |
  </Step>

  <Step title="Assign a reference per row">
    Deterministically, from the batch ID and row number, so re-uploading the same file cannot double-pay.
  </Step>

  <Step title="Show a confirmation before submitting">
    Recipient count, total per currency, and the largest single payout. Require a human to approve it.
  </Step>

  <Step title="Run the loop above">
    Submit, resolve by reference, reconcile on webhooks.
  </Step>
</Steps>

<Warning>
  A deterministic reference is what makes an accidental double upload harmless. Generating a random reference per run means the second upload pays everyone again.
</Warning>

## Refunds

Refunds are not self-serve in the dashboard. An agreed refund is processed as a payout to the customer's wallet address.

Setting `refund_address` when you initiate a transaction stores it on that transaction, so you have it when a refund comes up.

## Networks

<Warning>
  The recipient's address must be on the same network as the currency you send. USDT on BEP-20 sent to an ERC-20-only address is lost permanently.
</Warning>

| Currency | Network |
| --- | --- |
| USDT | BEP-20 (BNB Smart Chain) |
| USDC | BEP-20 (BNB Smart Chain) |
| BTC | Bitcoin |
| LTC | Litecoin |
| ETH | BEP-20 (BNB Smart Chain) |
| QDX | BEP-20 (BNB Smart Chain) |

<Note>
  The Wallets API supports a wider set of assets and networks than the Payments payout list above. If you are paying out programmatically, read the live `networks` array on the wallet rather than this table.
