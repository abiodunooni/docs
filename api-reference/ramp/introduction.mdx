The Ramp API is a REST API over JSON. It converts fiat to stablecoin and back, and settles both legs.

## Base URL

```
https://ramp-be.quidax.io/api/v1/merchants
```

Every path on these pages is relative to that root. There is no separate sandbox host — see [Testing](/ramp/testing).

## Authentication

Send your merchant secret key in the `x-private-key` header on every request.

```bash
curl 'https://ramp-be.quidax.io/api/v1/merchants/purchase_limits/buy?currency_symbol=ngn' \
  -H 'accept: application/json' \
  -H "x-private-key: $RAMP_SECRET_KEY"
```

A missing or wrong key returns:

```json
{ "status": "forbidden", "message": "Invalid private key", "data": null }
```

<Warning>
  The secret key is server-side only. Never ship it in browser or mobile code. The widget uses a separate public key (`pub_...`), which is safe on a client.
</Warning>

Get both keys from the merchant dashboard. The same secret key also signs your webhooks.

## Response format

Every response uses the same envelope.

```json
{
  "status": "ok",
  "message": "Transaction found",
  "data": {}
}
```

| `status` | HTTP | Meaning |
| --- | --- | --- |
| `ok` | 200 | Succeeded. |
| `bad_request` | 400 | Invalid, incomplete or duplicated request. |
| `forbidden` | 403 | Authentication failed. |
| `not_found` | 404 | The resource does not exist. |

Branch on `status`, not on `message`.

## References

Two identifiers travel with each transaction, and mixing them up is the most common integration error.

| Identifier | Who generates it | Format | Used for |
| --- | --- | --- | --- |
| `merchant_reference` | You | Your own scheme | Creating, refreshing, confirming, attaching accounts, refunds |
| `reference` | Quidax | `TRX-...` | Fetching a transaction |

Store both against your order record. A `merchant_reference` must be unique, and reusing one returns a duplicate transaction error.

## Amounts

Amounts are strings, not numbers, in both requests and responses. This preserves precision on assets with many decimal places. Parse them with a decimal type rather than a float.

```json
{ "from_amount": "3000.0", "to_amount": "1.927314" }
```

## Pagination

List endpoints accept these query parameters.

| Parameter | Default | Notes |
| --- | --- | --- |
| `page` | 1 | Positive integer. |
| `per_page` | 25 | Positive integer, maximum 50. |
| `status` | — | Filter by transaction status. |
| `from_currency` | — | Filter by source currency code. |
| `to_currency` | — | Filter by destination currency code. |
| `start_date` | — | `YYYY-MM-DD`. Must be sent with `end_date`. |
| `end_date` | — | `YYYY-MM-DD`. Must be sent with `start_date`. |

```bash
curl 'https://ramp-be.quidax.io/api/v1/merchants/on_ramp_transactions?page=1&per_page=50&start_date=2026-08-01&end_date=2026-08-31' \
  -H "x-private-key: $RAMP_SECRET_KEY"
```

The date filters are what you want for reconciliation runs.

List responses carry a `meta` object alongside `data`:

```json
{
  "status": "ok",
  "message": "Transactions fetched successfully",
  "data": [],
  "meta": {
    "page": 1,
    "per_page": 25,
    "total_count": 16,
    "total_pages": 1,
    "next_page": null
  }
}
```

Page until `next_page` is `null` rather than counting against `total_pages` yourself.

<Note>
  Validation errors on list endpoints return `message` and `data` only, without the `status` field the rest of the API uses. Handle a missing `status` rather than assuming it is present.
</Note>

## Idempotency and retries

Ramp keys transactions on your `merchant_reference`. If a request times out and you do not know whether it landed, retry with the same reference: a duplicate error confirms the original succeeded.

The mobile money OTP endpoint is idempotent, and resubmitting identical refund details in the same cycle is safe.
