Every Ramp response uses the same envelope, whether it succeeded or failed.

```json
{
  "status": "ok",
  "message": "Human-readable response message",
  "data": {}
}
```

| Field | Type | Description |
| --- | --- | --- |
| `status` | string | Result of the request. |
| `message` | string | Human-readable explanation. |
| `data` | object, array or null | Response payload on success, usually `null` on errors. |

## Response statuses

| `status` | HTTP | Meaning |
| --- | --- | --- |
| `ok` | 200 | The request succeeded. |
| `bad_request` | 400 | The request was invalid, incomplete, duplicated or could not be processed. |
| `forbidden` | 403 | Authentication failed, usually an invalid private key. |
| `not_found` | 404 | The transaction, refund, withdrawal or wallet does not exist. |
| `conflict` | 409 | A `merchant_reference` was reused with different details. Withdrawals only. |
| `unprocessable_entity` | 422 | A business rule rejected the request. Withdrawals only. |
| `internal_server_error` | 500 | Unexpected server error. Safe to retry with the same `merchant_reference`. |

<Tip>
  Branch on `status` rather than parsing `message`. Messages are written for humans and may be reworded; the status values are stable.
</Tip>

## Transaction statuses

`status` on the transaction itself, distinct from the response status above.

| Status | Terminal | Meaning |
| --- | --- | --- |
| `pending` | No | Created but not yet funded. |
| `processing` | No | Funds received. Conversion or payout under way. |
| `completed` | Yes | Both legs finished successfully. |
| `failed` | Yes | The transaction could not be completed. |
| `needs_attention` | No | One leg succeeded, the other did not. Under manual review. |
| `refunded` | Yes | Funds returned to the customer. |
| `abandoned` | Yes | Created but never funded. |
| `cancelled` | Yes | Cancelled before completion. |
| `swap_reversed` | Yes | A conversion was reversed. |

Credit your customer only on `completed`. `needs_attention` means Quidax is working on it, so hold rather than failing the order.

Leg statuses sit on the nested objects: `fiat_deposit.status`, `crypto_payout.status`, `crypto_deposit.status` and `fiat_payout.status`. A transaction can be `needs_attention` with `fiat_deposit.status` of `success` and `crypto_payout.status` of `failed`.

`error_message` on a fetched transaction carries the reason where one is available, and is `null` otherwise.

## Withdrawal statuses

Custodial withdrawals use their own, shorter set. There is no `needs_attention` — a withdrawal either lands or fails, and a failed one leaves the funds in your wallet.

| Status | Terminal | Meaning |
| --- | --- | --- |
| `pending` | No | Created and awaiting processing. |
| `processing` | No | Being processed. |
| `completed` | Yes | Settled on-chain. `txid` is populated. |
| `failed` | Yes | Could not be completed. Funds remain in your custodial wallet. |

## When a transaction needs attention

`needs_attention` is not a failure and not a terminal state. Money is held, not lost, and the resolution depends on which leg stalled.

<AccordionGroup>
  <Accordion title="The crypto deposit was more or less than the initiated amount" icon="equals">
    Quidax **holds the stablecoin** and waits for your decision. Nothing is converted, paid out or refunded until you answer.

    You have two options:

    | Your decision | What Quidax does |
    | --- | --- |
    | **Approve** | Processes the transaction at the amount actually received |
    | **Reject** | Refunds the deposit to your customer |

    This is a merchant decision by design — only you know whether crediting a customer who sent 99.4 USDT instead of 100 is acceptable in your product. Build an operational path for it before launch, because the transaction sits until someone answers.
  </Accordion>

  <Accordion title="The receiving bank rejected the fiat payout" icon="building-columns">
    Quidax retries the payout. If the customer's bank cannot receive the funds at all, Quidax asks you for an alternative bank account.

    The crypto side is already settled at this point, so the transaction is not unwound — it is redirected. Keep a way to reach the customer for new payout details after a transaction is confirmed.
  </Accordion>

  <Accordion title="The wrong asset or network was sent" icon="link-slash">
    Handled case by case. Contact support with the `merchant_reference` and the transaction hash.
  </Accordion>
</AccordionGroup>

<Warning>
  **Resolution is manual today.** There is no endpoint to approve or reject a held deposit, and no way to submit an alternative payout account through the API. Resolution runs through your merchant success manager or support.
</Warning>

## Failure modes worth handling

<AccordionGroup>
  <Accordion title="The customer paid the wrong amount" icon="equals">
    The provider rejects overpayment and underpayment on the virtual account and reverses the transfer. Nothing reaches Ramp.

    That means **no webhook fires**, the transaction stays `pending` until it abandons at 36 minutes, and the provider returns the money to the customer. Your customer will report paying while your system shows nothing.

    Show `amount_expected` prominently, discourage rounding, and treat post-payment silence as a wrong-amount signal rather than an incident. Full detail in [When a payment is rejected](/ramp/how-it-works#when-a-payment-is-rejected).
  </Accordion>

  <Accordion title="The customer never paid" icon="clock">
    An unfunded transaction is abandoned automatically — 36 minutes after creation on on-ramp, 24 hours on off-ramp. No webhook is emitted, so poll or reconcile if you need to detect it.
  </Accordion>

  <Accordion title="Someone else paid" icon="user-xmark">
    The paying account must belong to the customer you named on the transaction. A mismatch means the deposit is rejected and refunded, which starts the [refund flow](/ramp/refunds).

    Note this is about the *named* customer, not about sender and beneficiary being the same person — see [who counts as the customer](/ramp/how-it-works#rules-that-apply-to-every-transaction).
  </Accordion>

  <Accordion title="A duplicate deposit was made" icon="copy">
    The provider rejects the second deposit to the same virtual account and reverses it.
  </Accordion>

  <Accordion title="The wrong asset or network was sent" icon="link-slash">
    On off-ramp, sending a different asset, a different amount, or using the wrong network can push the transaction into `needs_attention` for manual review. The funds are held, not lost — see [when a transaction needs attention](#when-a-transaction-needs-attention) for what happens next and what Quidax needs from you.
  </Accordion>

  <Accordion title="A payout was reversed after acceptance" icon="rotate-left">
    A bank or mobile money provider can accept a payout and reverse it later. Quidax handles these manually and sends the fiat to an alternative account you provide.
  </Accordion>

  <Accordion title="A limit was breached" icon="gauge-high">
    The transaction is rejected before any money moves. Ramp never partially fills. Surface the message and offer a smaller amount where you can.

    Daily caps are per customer over a rolling 24-hour window, so a blocked customer regains headroom as their earlier transactions age out — not at midnight. There is no endpoint for remaining headroom; track it yourself if you want to catch this before the rejection. See [Transaction tiers](/ramp/coverage#transaction-tiers).
  </Accordion>
</AccordionGroup>

## Retrying safely

Ramp keys transactions on your `merchant_reference`, which makes safe retries straightforward:

- **A request timed out and you do not know if it landed.** Retry with the same `merchant_reference`. A duplicate error tells you the original succeeded.
- **A request failed validation.** Fix the input and retry with the same reference — nothing was created.
- **You want to start over.** Generate a new reference. Never reuse one across different transactions.

<Warning>
  Never retry a confirmed transaction with a new reference before checking the state of the original. You could generate a second bank account for a customer who has already paid into the first.
</Warning>
