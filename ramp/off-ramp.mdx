An off-ramp transaction, also called a sell, takes stablecoin from your customer and pays local currency to their bank or mobile money account.

```
create → refresh (optional) → attach payout account → confirm → customer sends → webhooks → complete
```

The extra step compared with on-ramp is attaching the payout account, and it has to happen **before** you confirm.

<Note>
  All requests go to `https://ramp-be.quidax.io/api/v1/merchants` and carry your secret key in the `x-private-key` header.
</Note>

## 1. Create the transaction

```bash
curl -X POST 'https://ramp-be.quidax.io/api/v1/merchants/custodial/off_ramp_transactions/initiate' \
  -H 'accept: application/json' \
  -H 'content-type: application/json' \
  -H "x-private-key: $RAMP_SECRET_KEY" \
  -d '{
    "from_currency": "usdt",
    "to_currency": "ghs",
    "from_amount": "3",
    "network": "bep20",
    "customer": {
      "email": "ada@example.com",
      "first_name": "Ada",
      "last_name": "Lovelace"
    },
    "merchant_reference": "order_67890"
  }'
```

```json Response
{
  "status": "ok",
  "message": "Transaction successfully initiated",
  "data": {
    "public_id": "3e9e395c-a8df-4694-97a9-237a0ea21b9b",
    "from_currency": "usdt",
    "to_currency": "ghs",
    "from_amount": "3.0",
    "to_amount": "33.64684",
    "reference": "TRX-ZTIKAIJPFA",
    "merchant_reference": "order_67890",
    "status": "pending",
    "stamp_charge": "0.0"
  }
}
```

The asset amount you send determines the fiat the customer receives. `to_amount` reflects the rate with fees and any markup already applied, and the Ramp fee is already deducted from it — it is what the customer gets, not a gross figure to net down.

<Warning>
  Off-ramp is priced **from the asset amount only**. There is no way to specify a target fiat payout and have Ramp derive the token amount required, on this endpoint or on the sell quote.

  If your product commits to a fiat figure before the customer sends anything, you derive the token amount yourself and absorb the rate movement. See [Guaranteeing a fiat amount to your customer](/ramp/rates-and-markup#guaranteeing-a-fiat-amount-to-your-customer).
</Warning>

## 2. Refresh the quote

```bash
curl -X PUT 'https://ramp-be.quidax.io/api/v1/merchants/custodial/off_ramp_transactions/order_67890/refresh' \
  -H 'content-type: application/json' \
  -H "x-private-key: $RAMP_SECRET_KEY" \
  -d '{ "from_currency": "usdt", "to_currency": "ghs", "from_amount": "3" }'
```

Refresh before the customer sends anything.

If the deposit arrives after the quote has expired, Ramp neither rejects it nor holds the funds — it re-quotes at the rate current when the deposit lands and settles on that. Plan for the rate at settlement, not the rate you last showed.

## 3. Fetch supported institutions

Pull the live list for the country and use each entry's `code` as the `bank_code` in the next step.

```bash
curl 'https://ramp-be.quidax.io/api/v1/merchants/custodial/banks?country=GH' \
  -H 'accept: application/json' \
  -H "x-private-key: $RAMP_SECRET_KEY"
```

```json Response
{
  "status": "ok",
  "message": "Banks successfully fetched",
  "data": [
    { "code": "0004", "name": "MTN", "public_id": "f9cf0f2d-da7b-40cd-be43-e2b2a82f68b4" },
    { "code": "0006", "name": "VODAFONE", "public_id": "9024ec7a-1394-45d8-8e1a-3df32b4392ba" },
    { "code": "0005", "name": "AIRTEL", "public_id": "207b1aac-af2a-4da7-832e-2a38c8a38644" },
    { "code": "280100", "name": "Access Bank", "public_id": "a1b49f16-2578-49e2-b04c-667231d08316" }
  ]
}
```

Pass `country=NG` for Nigeria. Fetch the list rather than hard-coding it, so newly supported institutions reach your integration without a release.

<Warning>
  **`code` is Ramp's own institution identifier. It is not the CBN or NIBSS bank code.**

  Take the value verbatim from this endpoint. Do not translate it from another namespace, do not assume a fixed width, and do not build your mapping from a 3-digit list you hold elsewhere — Access Bank is `044` to NIP and a different value here. Codes in this page and the API reference are illustrative; the endpoint is authoritative.

  Key your own bank mapping on `public_id`, which is stable, and treat `code` as the value you pass through unchanged.
</Warning>

<Tip>
  Mobile money providers and banks come back in the same list. For a GHS consumer flow you usually want to surface the mobile money entries first, since they settle faster and reach more customers.
</Tip>

## 4. Attach the payout account

```bash
curl -X POST 'https://ramp-be.quidax.io/api/v1/merchants/custodial/off_ramp_transactions/order_67890/bank_account' \
  -H 'content-type: application/json' \
  -H "x-private-key: $RAMP_SECRET_KEY" \
  -d '{
    "currency_code": "ghs",
    "bank_code": "0006",
    "account_number": "0123456789"
  }'
```

For GHS mobile money, `account_number` is the customer's mobile money number.

```json Response
{
  "status": "ok",
  "message": "Bank account successfully created and attached to off-ramp transaction",
  "data": {
    "public_id": "f5bf2c47-9581-4285-ab9d-124b8d89516d",
    "metadata": {
      "account_number": "0123456789",
      "bank_code": "0006",
      "slug": "VOD",
      "account_name": "Ada Lovelace"
    },
    "status": "active"
  }
}
```

<Warning>
  Ramp resolves the account and compares the resolved name against the customer name on the transaction. A mismatch returns `Name does not match` and the account is not attached. Surface this to your customer as a name problem rather than a generic failure — it is the most common reason an off-ramp stalls.
</Warning>

## 5. Confirm and get the deposit address

Only confirm once the payout account is attached.

```bash
curl -X POST 'https://ramp-be.quidax.io/api/v1/merchants/custodial/off_ramp_transactions/order_67890/confirm' \
  -H 'accept: application/json' \
  -H "x-private-key: $RAMP_SECRET_KEY"
```

```json Response
{
  "status": "ok",
  "message": "Address has been successfully created",
  "data": {
    "id": "1075784d-79ff-4e9c-816e-74a5eb2eb1ff",
    "address": "0x2c8cb922aede1464ec575c",
    "tag": null,
    "network": "bep20",
    "currency": "usdt",
    "assigned_at": "2026-06-16T16:59:24.353Z",
    "status": "assigned"
  }
}
```

<Warning>
  The customer must send the exact amount, in the correct asset, on the correct network. A different amount, asset or network can push the transaction into `needs_attention` for manual review.

  Where `tag` is not `null`, the customer must include it. Omitting a required tag or memo means the deposit is not credited automatically.
</Warning>

## Deposit detection

Ramp watches the assigned address and moves the transaction to `processing` when the deposit is accepted. Detection is asynchronous — nothing about your on-chain send is gated on it.

| | |
| --- | --- |
| Typical detection | Under a minute from confirmation on the network |
| What it includes | Network confirmations, plus screening to confirm the funds are not from a sanctioned source |
| Longer than that | Usually an upstream provider delay. Quidax Engineering investigates; the deposit is not lost |

Do not couple a deadline on your side — a signing window, a held quote, a customer-facing timer — to Ramp detecting the deposit. Send, record the transaction hash, and let `sell_transaction.processing` tell you when it landed.
</Warning>

If your flow has a hard timing constraint, raise it with your merchant success manager during onboarding rather than designing around the figure above.

## 6. Track it to completion

| Event | State |
| --- | --- |
| `sell_transaction.processing` | Deposit accepted. `crypto_deposit` populated, `fiat_payout` still `null`. |
| `sell_transaction.processing` | Payout under way. Both objects populated. |
| `sell_transaction.successful` | Complete. |
| `sell_transaction.failed` | Status is `needs_attention`. |

Fetch the transaction with the Quidax `reference` when you need to reconcile.

```bash
curl 'https://ramp-be.quidax.io/api/v1/merchants/off_ramp_transaction/TRX-ZTIKAIJPFA' \
  -H "x-private-key: $RAMP_SECRET_KEY"
```

## Stamp duty on NGN payouts

Nigerian stamp duty of ₦50 applies where the payout is ₦10,000 or more. It is deducted from the converted amount **after** conversion, so it does not appear in the quote.

For a 10 USDT payout at a rate of 1,378.46:

```
10 × 1,378.46  = 13,784.60 NGN
             −      50.00 NGN stamp duty
             = 13,734.60 NGN credited to the customer
```

If you show customers a net figure before they commit, subtract stamp duty yourself for payouts over the threshold.

## Transaction window

An off-ramp transaction that never receives its deposit is **abandoned after 24 hours**. That is generous compared with the 36-minute on-ramp window, because the customer has to make an on-chain transfer, but it still means a deposit address does not stay live indefinitely.

Abandonment does not emit a webhook. Poll the transaction or reconcile with the list endpoints if you need to detect it.

## Payout timing and cutoffs

**NGN payouts have no customer-facing cutoff window.** They are processed in real time, including at weekends and outside normal banking hours. There is no overnight queue and no Monday-morning batch, so you can promise your customers same-session settlement regardless of when they transact.

| Situation | What happens |
| --- | --- |
| Payout submitted at any hour, any day | Processed in real time |
| NIBSS or the receiving bank is unavailable | Ramp retries once the service is back. No action needed from you |
| The receiving bank rejects the payout | Ramp retries, or asks you for an alternative account. See [when a transaction needs attention](/ramp/errors#when-a-transaction-needs-attention) |

<Note>
  A retry after an outage means the transaction stays open longer than the typical figure, without failing. Do not time out an off-ramp on your side and tell the customer it failed — wait for `sell_transaction.successful` or `sell_transaction.failed`.
</Note>

## Payout reversals

A bank or mobile money provider can accept a payout and reverse it later. It is uncommon, and when it happens Quidax handles it manually and sends the fiat to an alternative account you provide. Watch for `sell_transaction.failed` and reconcile against the payout status rather than assuming acceptance is final.

## Checklist

1. Use a unique `merchant_reference` per transaction, and reuse it across refresh, attach and confirm.
2. Fetch the institution list before attaching a payout account.
3. Make sure the payout account name matches the customer name on the transaction.
4. Attach the payout account before confirming.
5. Tell the customer the exact amount, asset and network, and include the tag where one is returned.
6. Treat webhooks as the source of truth, and requery to reconcile.
