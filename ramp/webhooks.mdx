Webhooks are how Ramp tells you a transaction moved. Treat them as the source of truth for the final state of a transaction, and requery the API when you need to confirm.

## Set up your endpoint

<Steps>
  <Step title="Register your URL">
    Set your webhook URL in the merchant dashboard. It must be reachable over HTTPS. All events for your app, including refunds, are delivered to this one URL.
  </Step>

  <Step title="Capture the raw body">
    Signature verification runs against the exact bytes Ramp sent. Configure your framework to expose the raw request body before any JSON parsing middleware touches it.
  </Step>

  <Step title="Verify, store, respond">
    Verify the signature, persist the event, return `2xx`, and do your business logic asynchronously.
  </Step>
</Steps>

## Request format

Ramp sends a `POST` with these headers:

```http
Content-Type: application/json
User-Agent: Quidax-Ramp
X-Ramp-Signature: <hmac_sha256_signature>
```

Every payload has the same shape: an `event` name and a `data` object.

```json
{
  "event": "buy_transaction.successful",
  "data": {
    "mode": "buy",
    "status": "completed",
    "merchant_reference": "order_12345"
  }
}
```

<Warning>
  Branch on `event`, not on `data.status`. They are different fields with different vocabularies, and they do not mirror each other — `buy_transaction.successful` carries `data.status: "completed"`, and `buy_transaction.failed` carries `data.status: "needs_attention"`.

  `event` is the reliable discriminator. Treat `data.status` as detail about the transaction, not as the name of what happened.
</Warning>

| Event | `data.status` you should expect |
| --- | --- |
| `buy_transaction.processing` | `processing` |
| `buy_transaction.successful` | `completed` |
| `buy_transaction.failed` | `needs_attention` |
| `sell_transaction.processing` | `processing` |
| `sell_transaction.successful` | `completed` |
| `sell_transaction.failed` | `needs_attention` |
| `custodial_withdraw.success` | `completed` |
| `custodial_withdraw.failed` | `failed` |

## Verify the signature

Ramp signs the webhook with **HMAC-SHA256 over the raw request body**, hex encoded, using your app's latest active secret key. Compare that digest with `X-Ramp-Signature`.

<CodeGroup>
```js Node.js
import crypto from "crypto";

export function verifyRampSignature(rawBody, signature, secretKey) {
  const expected = crypto
    .createHmac("sha256", secretKey)
    .update(rawBody)
    .digest("hex");

  if (expected.length !== signature.length) return false;

  return crypto.timingSafeEqual(Buffer.from(expected), Buffer.from(signature));
}
```

```js Express
import express from "express";

const app = express();

app.post(
  "/webhooks/ramp",
  express.raw({ type: "application/json" }),
  (req, res) => {
    const signature = req.headers["x-ramp-signature"];

    if (!verifyRampSignature(req.body, signature, process.env.RAMP_SECRET_KEY)) {
      return res.sendStatus(401);
    }

    const event = JSON.parse(req.body.toString());

    // Persist first, process later.
    enqueue(event);

    res.sendStatus(200);
  },
);
```

```python Python
import hmac
import hashlib

def verify_ramp_signature(raw_body: bytes, signature: str, secret_key: str) -> bool:
    expected = hmac.new(
        secret_key.encode(),
        raw_body,
        hashlib.sha256,
    ).hexdigest()

    return hmac.compare_digest(expected, signature)
```

```go Go
package ramp

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/hex"
)

func VerifySignature(rawBody []byte, signature, secretKey string) bool {
	mac := hmac.New(sha256.New, []byte(secretKey))
	mac.Write(rawBody)
	expected := hex.EncodeToString(mac.Sum(nil))

	return hmac.Equal([]byte(expected), []byte(signature))
}
```

```php PHP
<?php

function verify_ramp_signature(
    string $rawBody,
    string $signature,
    string $secretKey
): bool {
    $expected = hash_hmac('sha256', $rawBody, $secretKey);

    return hash_equals($expected, $signature);
}
```

```ruby Ruby
require 'openssl'

def verify_ramp_signature(raw_body, signature, secret_key)
  expected = OpenSSL::HMAC.hexdigest('SHA256', secret_key, raw_body)

  OpenSSL.secure_compare(expected, signature)
end
```

```java Java
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.util.HexFormat;

public final class RampSignature {
    public static boolean verify(byte[] rawBody, String signature, String secretKey)
            throws Exception {
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(
            secretKey.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));

        String expected = HexFormat.of().formatHex(mac.doFinal(rawBody));

        return MessageDigest.isEqual(
            expected.getBytes(StandardCharsets.UTF_8),
            signature.getBytes(StandardCharsets.UTF_8));
    }
}
```

```csharp C#
using System.Security.Cryptography;
using System.Text;

public static class RampSignature
{
    public static bool Verify(byte[] rawBody, string signature, string secretKey)
    {
        using var hmac = new HMACSHA256(Encoding.UTF8.GetBytes(secretKey));
        var expected = Convert.ToHexString(hmac.ComputeHash(rawBody)).ToLowerInvariant();

        return CryptographicOperations.FixedTimeEquals(
            Encoding.UTF8.GetBytes(expected),
            Encoding.UTF8.GetBytes(signature));
    }
}
```
</CodeGroup>

<Note>
  Each example compares digests in constant time. A plain `==` on the signature leaks timing information, and the fix costs nothing.
</Note>

<Warning>
  Verify against the raw body. Parsing and re-serialising the JSON changes key order and whitespace, which changes the digest and makes every signature fail.
</Warning>

## Respond and retry

| Behaviour | Detail |
| --- | --- |
| Expected response | Any `2xx`. Ramp reads only the status code. |
| Timeout | 10 seconds. |
| Treated as failed | A timeout, an unreachable endpoint, or a non-`2xx` response. |

A failed delivery is retried up to five times, backing off each time:

| Retry | Sent after the previous attempt | Elapsed since the first |
| --- | --- | --- |
| 1 | 1 minute | 1 minute |
| 2 | 2 minutes | 3 minutes |
| 3 | 4 minutes | 7 minutes |
| 4 | 8 minutes | 15 minutes |
| 5 | 16 minutes | 31 minutes |

After the fifth retry the event is dropped. So a brief outage is absorbed, but an endpoint down for more than about half an hour loses events permanently — reconcile with the [list endpoints](/api-reference/ramp/transactions/list-on-ramp-transactions) rather than assuming delivery.

Because deliveries retry, your handler must be idempotent. Key on the combination of `event`, `merchant_reference` and, for refunds, `refund_reference`.

<Tip>
  Acknowledge before you process. Verify the signature, write the event to a queue or table, then return `2xx`. Doing settlement work inline is what pushes handlers past the timeout and triggers duplicate deliveries.
</Tip>

## Events

Subscribe to all three events for each direction you support, and be explicit about which one credits your customer.

| Event | Your action |
| --- | --- |
| `*_transaction.processing` | Store idempotently and return `2xx`. **Do not credit the customer.** May arrive more than once. |
| `*_transaction.successful` | Terminal success. **Credit the customer exactly once**, and verify the balance moved. |
| `*_transaction.failed` | **Do not credit.** Record `error_message` and trigger your support escalation. |
| `custodial_withdraw.*` | Terminal state of a withdrawal from your custodial wallet. Key on `public_id` or `merchant_reference`. |

## Handling patterns

<AccordionGroup>
  <Accordion title="Out-of-order and duplicate delivery" icon="shuffle">
    Retries and network conditions mean an event can arrive twice, or a `processing` event can land after `successful`. Store the status you receive, but never move a transaction backwards from a terminal state. If your record already says `completed`, ignore a later `processing`.
  </Accordion>

  <Accordion title="Webhook before your own record exists" icon="clock">
    A webhook can arrive before your database has committed the transaction you just created. Look the transaction up by `merchant_reference`, and if you do not find it, retry after a short delay rather than discarding the event.
  </Accordion>

  <Accordion title="Missed events" icon="wifi">
    If your endpoint was down, reconcile by fetching each open transaction, or by listing transactions with `start_date` and `end_date`. Do not depend on webhook delivery alone for financial state.

    <Card title="List on-ramp transactions" icon="code" href="/api-reference/ramp/transactions/list-on-ramp-transactions" horizontal />
  </Accordion>

  <Accordion title="Secret key rotation" icon="key">
    Signatures use your app's latest active secret key. When you rotate, accept signatures from both the old and new key for a short window so events in flight still verify.
  </Accordion>
</AccordionGroup>
