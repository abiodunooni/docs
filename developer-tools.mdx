## The differences that catch people out

| | Ramp | Payments | Wallets |
| --- | --- | --- | --- |
| Auth header | `x-private-key` | `Authorization: Bearer` | `Authorization: Bearer` |
| Webhook algorithm | HMAC | HMAC **SHA512** | HMAC **SHA256** |
| Webhook signs | Body | Body | **`timestamp.body`** |
| Sandbox | No | **Yes** | No |
| Branch errors on | `status` | HTTP code | `data.code` |

<Warning>
  The webhook row is the one that hurts. A handler written for one product will silently fail to validate another's events — no error, just nothing processed.
</Warning>

## Conventions that hold everywhere

<AccordionGroup>
  <Accordion title="Give value on the webhook, not on a redirect" icon="webhook">
    A customer who closes the tab after paying still paid. One who returns without paying has not.
  </Accordion>

  <Accordion title="Re-query before giving value" icon="magnifying-glass">
    The webhook says something happened; the API says what is true now. Where money is involved, act on the second.
  </Accordion>

  <Accordion title="Process idempotently" icon="fingerprint">
    Every product can deliver the same event twice. Key on the resource ID and check before crediting.
  </Accordion>

  <Accordion title="Generate references before you call" icon="hashtag">
    A reference created after a successful response cannot help you with a timeout, which is the only case you need it for.
  </Accordion>

  <Accordion title="Never retry money with a new reference" icon="triangle-exclamation">
    Look up the original first. If it landed, you have already paid — and an on-chain payout cannot be recalled.
  </Accordion>

  <Accordion title="Fetch reference data, do not hard-code it" icon="list-check">
    Currencies, networks, limits and fees all change. Every product exposes them, and hard-coding means a release each time one moves.
  </Accordion>

  <Accordion title="Secret keys are server-side only" icon="lock">
    Never in client code, never committed, never logged.
  </Accordion>
</AccordionGroup>
